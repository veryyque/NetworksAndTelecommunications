В комментарии к строке 23 `ClientHandler.swift` написано «длины пути», но фактически проверяется длина переданного имени.

**Что сказать:** «Открываю файл по переданному пути, проверяю его тип и размер. Из пути извлекаю имя и проверяю его длину после кодирования в UTF-8».

Формат обмена:

```text
Клиент → сервер:
[4 байта: длина имени UInt32, big-endian]
[N байт: имя UTF-8]
[8 байтов: размер содержимого UInt64, big-endian]
[fileSize байтов: исходное содержимое]

Сервер → клиент:
[1 байт: 1 — успех, 0 — ошибка]
```

Содержимое не кодируется в UTF-8: передаются исходные байты любого обычного файла. Буфер 64 КиБ — размер блока приложения, а не размер TCP-сегмента.

**Что сказать:** «Я использую собственный бинарный протокол поверх TCP. Размеры полей позволяют серверу правильно разобрать поток, а циклы учитывают частичную передачу».

## 4. Сохранение в uploads с безопасным именем

| Файл | Строки | Что реализовано |
|---|---|---|
| `Server/ClientHandler.swift` | 27–34 | Проверка UTF-8 и нулевого байта, выделение последней компоненты; запрет пустого имени, `.`/`..` и `/`. |
| `Server/ClientHandler.swift` | 38–45 | Создание относительного каталога `uploads`, открытие с `O_DIRECTORY | O_NOFOLLOW`, вызов `createUpload`. |
| `Common/FileUtils.swift` | 18–30 | Сначала исходное имя, затем варианты с числовым суффиксом перед расширением. |
| `Common/FileUtils.swift` | 31–34 | `openat` относительно каталога; `O_CREAT | O_EXCL | O_NOFOLLOW` исключают перезапись и использование ссылки. |
| `Server/ClientHandler.swift` | 71–73 | Передача полученного блока в `writeAll`. |
| `Common/FileUtils.swift` | 4–16 | Полная запись блока в созданный файл. |

`../../secret.txt` не используется как путь: выделяется `secret.txt`. Открытие каталога с `O_NOFOLLOW` отклоняет символическую ссылку вместо `uploads`. Создание выполняется относительно дескриптора этого каталога. При конфликте имён пробуются `test_1.txt`, `test_2.txt` и далее. Проверка отсутствия имени и создание выполняются атомарно через `O_EXCL`, что важно для нескольких клиентов.

Каталог определяется текущей рабочей папкой сервера, а не местом расположения исходников. Файловая система может иметь собственный предел длины имени ниже 4096 байт; ошибка создания такого файла обрабатывается как неуспешная передача.

**Что сказать:** «Сохраняю файл в uploads, используя только безопасное имя. Если имя занято, добавляю номер без перезаписи существующего файла».

## 5. Мгновенная и средняя скорость, интервал 3 секунды

| Файл | Строки | Что реализовано |
|---|---|---|
| `Server/ClientHandler.swift` | 10–11 | Подпись клиента: IP и дескриптор, позволяющий различать одновременные подключения с одного IP. |
| `Server/ClientHandler.swift` | 55–56 | Отдельная статистика на соединение; принудительный итоговый вывод через `defer`. |
| `Server/ClientHandler.swift` | 69–74 | Добавляются только реально полученные байты содержимого; после записи проверяется время вывода. |
| `Server/TransferStatistics.swift` | 4–12 | Начальное время, время последнего вывода и два независимых счётчика. |
| `Server/TransferStatistics.swift` | 15–18 | `add` увеличивает общий счётчик и счётчик интервала. |
| `Server/TransferStatistics.swift` | 20–30 | Условие `force || interval >= 3`, две формулы, вывод bytes/s, сброс счётчика интервала. |

Формулы:

```text
instant = bytesSinceLastPrint / intervalSeconds
average = totalReceivedBytes / totalSeconds
```

Заголовок прочитан до создания статистики и не добавляется в счётчики. Время начинается перед приёмом содержимого и включает ожидание данных и запись. Для короткой и пустой передачи вывод обеспечивается `force: true`. При ошибке до создания статистики (например, неверном имени) статистика содержимого ещё не существует.

**Уточнение реализации:** проверка трёх секунд происходит после блока. Пока `recv` блокируется без данных, периодических сообщений нет. Такой способ прямо разрешён в подробной формулировке задания; независимого таймера, печатающего строго каждые три секунды при простое, в текущем коде нет.

**Что сказать:** «У каждого клиента собственная статистика. Считаю только содержимое, проверяю интервал после блоков и обязательно вывожу итог, даже если передача короче трёх секунд».

## 6. Проверка полученного размера, статус и закрытие соединения

| Файл | Строки | Что реализовано |
|---|---|---|
| `Server/ClientHandler.swift` | 58–69 | Счётчик фактических байтов; чтение ограничено остатком; ошибка при раннем EOF или ошибке recv. |
| `Server/ClientHandler.swift` | 71–73 | Каждый принятый блок полностью записывается через `writeAll`. |
| `Common/FileUtils.swift` | 7–14 | Цикл частичных записей; ошибка write прерывает приём. |
| `Server/ClientHandler.swift` | 76–80 | Проверка `receivedBytes == size`, закрытие файла с проверкой результата, отметка успешного сохранения. |
| `Server/ClientHandler.swift` | 12–18 | Успех отправляется только после возврата `receiveFile`; при ошибке — попытка отправить 0. |
| `Server/ClientHandler.swift` | 9 | Закрытие соединения при выходе из `run`. |
| `Common/TransferProtocol.swift` | 8–9 | Значения статусов успеха и ошибки. |

Хотя счётчик увеличивается до записи блока, ошибка `writeAll` вызывает `throw`, поэтому одного совпадения счётчика недостаточно для отправки успеха. Успех означает, что весь путь записи прошёл без ошибки. Проверяется число байтов приёма после записи всех блоков; повторное чтение файла для измерения размера не выполняется. `fsync` для гарантии сохранности при отключении питания не используется — это не требовалось.

Если файл сохранён, но отправить подтверждение не удалось, файл остаётся на сервере, а клиент не объявляет успех без статуса 1.

**Что сказать:** «Только после полного приёма, успешной записи, проверки размера и закрытия файла отправляю 1. При ошибке пытаюсь отправить 0, затем соединение закрывается».

| Файл | Строки | Что реализовано |
|---|---|---|
| `Client/TCPClient.swift` | 18 | Закрытие исходного файла через defer. |
| `Client/TCPClient.swift` | 34 | Закрытие клиентского сокета через defer. |
| `Server/ClientHandler.swift` | 9 | Закрытие принятого соединения. |
| `Server/ClientHandler.swift` | 44 | Закрытие дескриптора каталога uploads. |
| `Server/ClientHandler.swift` | 48–53 | Закрытие выходного файла при ошибке и попытка удалить частичную загрузку. |
| `Server/ClientHandler.swift` | 77–79 | Явное закрытие выходного файла перед успехом; -1 предотвращает повторное закрытие. |
| `Server/TCPServer.swift` | 11 | Закрытие слушающего сокета при выходе из run. |
| `Server/TCPServer.swift` | 29–34 | Инициализация и освобождение атрибутов pthread; режим detached. |
| `Server/TCPServer.swift` | 48–55 | Передача удержанного обработчика потоку; при ошибке создания — release и close. |
| `Server/TCPServer.swift` | 61–64 | takeRetainedValue возвращает удержание под управление ARC; завершение клиентского потока. |
| `Common/SocketUtils.swift` | 48 | Освобождение списка адресов через freeaddrinfo. |
| `Common/SocketUtils.swift` | 53–57 | Закрытие сокета неудачной попытки подключения. |

Массивы и Swift-объекты управляются автоматически. FileHandle и отдельное ручное выделение памяти для context не используются: передаётся удержанный Swift-объект.

Уточнения: входной файл клиента закрывается при выходе из sendFile, то есть после ожидания ответа; атрибуты pthread живут весь серверный run. Это немного дольше последнего использования конкретных данных, но ресурсы освобождаются на предусмотренных путях выхода. Большинство очистительных close вызываются без проверки результата; close выходного файла перед успехом проверяется явно. При завершении процесса сигналом ОС закрывает дескрипторы, но Swift defer может не выполниться, поэтому удаление частичного файла при принудительной остановке не гарантируется.

**Что сказать:** «Ресурсы освобождаются через defer, явный close, freeaddrinfo и механизм detached. Удержание объекта обработчика сбалансировано при успешном и неуспешном создании потока».

## 9. Параллельные клиенты, немедленный возврат к accept

| Файл | Строки | Что реализовано |
|---|---|---|
| `Server/TCPServer.swift` | 33–34 | Задание PTHREAD_CREATE_DETACHED до создания клиентских потоков. |
| `Server/TCPServer.swift` | 37–44 | Цикл accept; после запуска обработчика сразу начинается следующая итерация. |
| `Server/TCPServer.swift` | 47–57 | Создание отдельного ClientHandler и вызов pthread_create. |
| `Server/TCPServer.swift` | 61–64 | Функция нового потока вызывает handler.run(). |
| `Server/ClientHandler.swift` | 45–58 | У каждого обработчика собственные файл, статистика, буфер и счётчик. |

`pthread_join` в реализации нет. Вызов `startClientThread` ждёт только выполнения операции создания потока, а не передачи файла. Планирование потоков выполняет ОС. Если файлы очень маленькие, передачи могут успевать завершаться до запуска следующего клиента, хотя сервер поддерживает параллельную обработку.

**Что сказать:** «Один поток обслуживает одно соединение. Главный поток после pthread_create возвращается к accept и не ждёт завершения клиента».

## 10. Ошибка клиента не прекращает работу сервера

| Файл | Строки | Что реализовано |
|---|---|---|
| `Server/ClientHandler.swift` | 8–18 | Локальный do/catch, вывод ошибки, попытка отправить failure и закрытие сокета через defer. |
| `Server/ClientHandler.swift` | 48–53 | Очистка незавершённого файла при обычном выходе с ошибкой. |
| `Server/ClientHandler.swift` | 64–68 | Ошибка recv и раннее закрытие соединения прерывают только текущий приём. |
| `Common/FileUtils.swift` | 9–13 | Ошибка записи распространяется через throw в обработчик клиента. |
| `Server/ServerApplication.swift` | 7 | SIGPIPE игнорируется, чтобы запись в закрытый сокет не завершала весь процесс. |
| `Server/TCPServer.swift` | 38–43 | После ошибки accept цикл продолжает ожидать подключения. |
| `Server/TCPServer.swift` | 53–56 | Ошибка pthread_create освобождает ресурсы конкретного клиента без остановки сервера. |

В `ClientHandler` нет вызова exit: после обработки ошибки завершается его run и функция потока. Общий цикл accept остаётся работать. Доставка статуса ошибки возможна только пока соединение позволяет отправку. `exit(1)` в ServerApplication относится к ошибкам запуска самого сервера, например занятому порту.

**Что сказать:** «Ошибки передачи обрабатываются в клиентском потоке. Соединение закрывается, а слушающий сервер и остальные обработчики продолжают работу».
