# Лабораторная №4 · Змейка

Приложение для macOS 14 и новее показывает игры локальной сети и сервера курса, а также позволяет создать общую игру в локальной сети.

## Запуск

Откройте `Snake.xcodeproj`, выберите схему **Snakes** и устройство **My Mac**. Нажмите **⌘R** для запуска или **⌘U** для тестов. При первом открытии Xcode загрузит SwiftProtobuf 1.30.0.

Чтобы проверить сервер, введи имя игрока и новое имя игры, выбери **Создать игру → На сервере курса**. После появления поля нажми **Открыть веб-наблюдатель** и найди игру по этому имени. Пока смотришь, оставь приложение подключённым. Стрелки и WASD передают повороты на сервер. Для серверной игры размер поля, запас еды и интервал выбирает сервер.

Те же действия из терминала:

```sh
open Snake.xcodeproj
xcodebuild -project Snake.xcodeproj -scheme Snakes -destination 'platform=macOS' -derivedDataPath .build/xcode build
xcodebuild -project Snake.xcodeproj -scheme Snakes -destination 'platform=macOS' -derivedDataPath .build/xcode test
```

Для запуска трёх независимых экземпляров после сборки:

```sh
for i in 1 2 3; do open -n .build/xcode/Build/Products/Debug/Snakes.app; done
```

# Змейка по сети

Реализуйте многопользовательскую игру «Змейка». Несколько пользователей играют
на общем поле: каждый управляет своей змейкой, собирает еду и набирает очки,
избегая столкновений. Одну игру могут вести программы разных студентов:
они должны быть совместимы между собой.

Баллов за задачу: **5**. Дедлайн объявляется отдельно для текущего учебного года.

## Что должно уметь приложение

Каждый экземпляр программы должен позволять пользователю:

1. **Создать игру**: задать имя игры, своё имя и параметры поля, затем начать играть.
2. **Найти игру**: увидеть единый список игр из локальной сети и с фиксированного
   сервера курса, доступного через Интернет. Оба источника опрашиваются автоматически;
   адрес сервера задаётся курсом, вводить его при просмотре списка не нужно.
3. **Присоединиться** к выбранной игре как игрок или наблюдатель.
4. **Играть**: управлять змейкой и видеть общее поле и очки участников.
5. **Смотреть и возвращаться к игре**: прекратить управление без выхода из сессии,
   а затем получить новую змейку, если есть место. После гибели змейки пользователь
   тоже остаётся наблюдателем и может вернуться к игре.
6. **Полностью выйти** из игры. Остальные участники продолжают сессию.

Игра должна продолжаться при отказе ведущего узла, если есть доступный заместитель.
Гибель змейки ведущего или заместителя не меняет их сетевые обязанности.
Если продолжение невозможно, программа сообщает об ошибке и завершает сессию
без зависания интерфейса. Потери, дублирование и перестановки сетевых пакетов
не должны приводить к повторному выполнению действий, зависанию или утечкам ресурсов;
точные гарантии при отказе ведущего описаны в разделе о смене MASTER.

Разрабатывать собственного робота не требуется.

## Сервер курса и веб-наблюдатель

Сервер курса доступен по адресу **`snakes.ippolitov.me:9193/UDP`**
и использует тот же протокол **v2**. Задайте этот адрес в конфигурации клиента
как фиксированный источник интернет-каталога. DNS-имя разрешается в IPv4;
для обмена игровыми сообщениями используется UDP, а не HTTP.

- **Найти игру:** отправьте серверу DiscoverMsg. В ответ приходят
  AnnouncementMsg с серверными играми; объединяйте их с локальными играми
  в одном списке по правилам раздела «Обнаружение игр».
- **Присоединиться:** отправьте JoinMsg с именем выбранной игры и нужным
  requested_status (PLAYING или VIEWING).
- **Создать игру на сервере:** отправьте JoinMsg с новым непустым именем игры;
  укажите то же game_name в оболочке GameMessage. Сервер создаст игру со
  случайными допустимыми параметрами и роботом, присоединит вас и пришлёт
  конфигурацию в AnnouncementMsg. ACK на Join и конфигурацию ожидайте по
  правилам раздела «Подключение до получения конфигурации».
- **Пригласить робота в свою игру:** клиент в роли MASTER отправляет на сервер
  unicast AnnouncementMsg со своей игрой. Сервер присоединяется обычным JoinMsg
  к endpoint отправителя; клиент должен обрабатывать его как другого участника.

[Веб-наблюдатель](https://snakes.ippolitov.me/) показывает серверные игры,
поле и очки в браузере. Он предназначен только для просмотра; для управления
змейкой нужен ваш клиент. Используйте его для проверки, что действия клиента
отражаются в состоянии игры.

## Правила игры

### Поле и параметры

Поле — прямоугольная сетка с замкнутыми противоположными сторонами:
выйдя за один край, змейка появляется с другого (дискретный тор).
Левая верхняя клетка — (0, 0), x растёт вправо, y — вниз.
Змейка состоит из соседних клеток: голова, тело, хвост. Она может пересекать
границы поля несколько раз.

Параметры задаются до создания игры и далее не меняются:

| Параметр | Допустимые значения |
| --- | --- |
| Ширина и высота поля | 10..100 клеток каждая, до 100×100 |
| Запас еды, не зависящий от числа змеек | 0..10 |
| Интервал между ходами | 100..3000 мс |

Ограничения одной игры:

- до **6 подключённых участников**, включая наблюдателей;
- до **4 змеек** одновременно: не более четырёх участников играют, остальные смотрят;
- длина каждой змейки — **2..32 клетки**, включая голову;
- непустое имя игрока — до **24 байт UTF-8**, имя игры — до **32 байт UTF-8**;
- текст ошибки — до **128 байт UTF-8**.

У играющего участника ровно одна змейка, у наблюдателя её нет. При смерти,
выходе, потере связи или переходе к просмотру змейка удаляется. Змейки
без подключённого владельца не продолжают движение.

### Появление змейки

Начальная длина змейки — две клетки. Это правило действует при создании игры,
присоединении к ней в качестве игрока и возвращении из режима просмотра.
Для размещения змейки ищется квадрат 5×5 без клеток других змеек,
с учётом замыкания поля. Голова ставится в центр, хвост — в случайную допустимую
соседнюю клетку. Обе клетки должны быть без еды. Если вариант не подходит,
проверяются остальные положения хвоста и квадраты. Голова направлена от хвоста.

Если свободного места нет или уже существуют четыре змейки, войти игроком
или вернуться к игре нельзя. Наблюдение не требует свободного места на поле,
но учитывается в лимите шести участников.

### Еда

Целевое **минимальное** количество еды — запас еды + число змеек.
Еда размещается случайно на пустых клетках, по одной единице на клетку.
Если клеток мало, размещается сколько возможно. Погибшие и удалённые змейки
не превращаются в еду. После движения, смертей, присоединения, выхода и смены
статуса ведущий пополняет еду до цели, если её недостаточно. При уменьшении
числа змеек существующая лишняя еда остаётся.
Начальная еда создаётся тем же пополнением; произвольно добавлять еду нельзя.

### Движение, столкновения и очки

Все змейки двигаются одновременно с заданным интервалом. Игрок выбирает
направление для следующего хода. Разворот головы в клетку шеи запрещён.
Наблюдатели не управляют змейками.

Переход рассчитывается одновременно для всех змей:

1. Голова продвигается на одну клетку. Если там была еда, владелец получает
   +1 очко; хвост остаётся на месте только при длине до хода менее 32 клеток.
   При длине 32 еда также съедается, но хвост освобождается и длина не меняется.
   Если еды не было, хвост освобождается.
2. По получившимся положениям всех змей определяются столкновения. Своя новая
   голова сама по себе не препятствие; своё тело — препятствие. Вход в любую
   чужую клетку, включая голову, убивает вошедшую змейку. Несколько голов на
   одной клетке погибают все. Обмен клетками голов убивает их, если после
   движения целевые клетки остались заняты телами.
3. Владелец змейки получает +1 за каждую чужую голову, врезавшуюся в неё,
   независимо от собственной гибели. Столкновение с собой очков не даёт.
   При столкновении N голов каждый получает N-1 очко за столкновения и очко
   за еду, если она была в целевой клетке.
4. Погибшие змейки удаляются. Их владельцы переходят
   к просмотру, сохраняя сетевые роли. Затем пополняется еда.

Поэтому можно преследовать освобождающийся хвост. Если преследуемая змейка
съест еду при длине менее 32, хвост не освободится и преследователь погибнет.
Если несколько голов вошли в еду, все получают очко за еду, растут до предела 32 и затем погибают.
Очки сохраняются при смерти, просмотре и возврате к игре. После выхода участника
хранить его очки не требуется.

### Просмотр и завершение игры

Переход к просмотру удаляет змейку, сохраняя имя, очки и сетевую роль участника.
Возвращение создаёт новую змейку по тем же правилам, что и вход игроком;
очки сохраняются. Если места нет, участник остаётся наблюдателем.
Полный выход удаляет участника и его змейку.

Игра продолжается, пока подключён хотя бы один участник, даже если все наблюдают.
Выход последнего участника завершает игру; сохранять её не требуется.

## Интерфейс

Интерфейс может быть графическим или текстовым. Поле и очки показываются
на одном экране; наблюдатели показаны отдельно или помечены. Сетевые роли
и участие в игре отображаются отдельно.

Должны быть доступны действия из раздела «Что должно уметь приложение».
**«Смотреть / прекратить играть»** и **«Выйти из игры»** — разные действия.
Параметры создаваемой игры вводятся любым разумным способом.
Управление должно быть удобным для устройства: WASD без Enter, геймпад,
свайпы или кнопки. Список игр и сообщения об ошибках обновляются без блокировки
интерфейса. Недоступность одного источника игр не мешает пользоваться другим.

[Макет](snakes_interface.png) показывает единый список игр, поле и участников
с отдельными сетевыми ролями и статусами. В примере ведущий наблюдает,
а заместитель играет; возвращение к игре и полный выход — разные действия.
Макет иллюстративный и не задаёт обязательный стиль оформления.
Показывайте целевое количество еды (запас еды + число змеек)
и отдельно фактическое количество. Требования к интерфейсу задаются этим текстом.

## Протокол и сетевая реализация

Следующие разделы задают общий способ обмена сообщениями, необходимый
для совместимости программ студентов. Формат сообщений определён в
[snakes.proto](src/main/protobuf/snakes.proto). Используется протокол **v2**.

### Модель участников и состояния

| Характеристика | Значения | Назначение |
| --- | --- | --- |
| `NodeRole` | MASTER, DEPUTY, NORMAL | Рассчитывает состояние, служит преемником или следует за MASTER |
| `PlayerStatus` | PLAYING, VIEWING | Управляет живой змейкой или смотрит |

Любой статус совместим с любой сетевой ролью. В игре ровно один MASTER; если
участников хотя бы два — ровно один DEPUTY. Остальные — NORMAL. MASTER назначает
DEPUTY из любых NORMAL, включая наблюдателей, сразу после появления первого
кандидата. Если DEPUTY выходит или пропадает, назначается новый.
Назначение передаётся через NodeRoleChangeMsg, остальные узнают роль из **StateMsg**.
В NodeRoleChange указывается sender_role (роль отправителя), receiver_role
(роль адресата) или оба поля; хотя бы одно обязательно. Номер state_order
привязывает уведомление к изменённому состоянию. Устаревшее уведомление
подтверждается без применения; сообщение не может отменить более новый снимок.

PlayerType.HUMAN/ROBOT — отдельное свойство; реализовывать робота не требуется.
У PLAYING ровно одна змейка, у VIEWING её нет. Каждая змейка принадлежит
подключённому игроку; при смерти, выходе, потере связи или переходе к просмотру
она удаляется. Отдельного состояния змейки и движения без владельца нет.

Топология — звезда: MASTER рассчитывает состояние и рассылает его всем участникам,
включая наблюдателей. После расчёта каждого хода MASTER публикует итоговый
StateMsg с учётом смертей, смены статусов и пополнения еды. Клиенты принимают
эти авторитетные снимки.

В GameConfig ширина и высота задаются полями width и height, запас еды —
food_static, интервал ходов — state_delay_ms. Целевое количество еды равно
food_static + число змеек.

Приложение проверяет диапазоны и смысл полей: комментарии `.proto` не выполняют
валидацию. Отсутствующие optional-поля конфига получают значения по умолчанию из схемы.

ID положительный и не переиспользуется **за всё время игры**. GameState хранит
next_player_id выше всех выданных ID, включая вышедших участников.
Новый MASTER наследует этот счётчик. Для возможности хранить следующий ID выдавать
INT32_MAX нельзя; при исчерпании диапазона новых участников не принимают.
Очки находятся в диапазоне 0..INT32_MAX; прибавление насыщается на INT32_MAX.
state_order неотрицателен, сохраняется при failover и увеличивается при публикации каждого
изменённого состояния: после хода, присоединения, выхода, смены роли или статуса.
Изменения между ходами не двигают змей и не сдвигают расписание ходов. При исчерпании
диапазона игра завершается без переполнения.

### Кодирование змейки

Направление головы задаётся Direction в поле head_direction.
Кодирование змейки: абсолютная координата головы, затем ненулевые осевые смещения
до поворотов и хвоста. Это фактический путь тела, не кратчайший путь по тору.
При восстановлении клеток координаты нормализуются по ширине/высоте; клетка
стыка отрезков не дублируется. Нулевая компонента смещения не записывается.
Самоврезание — столкновение головы с телом своей змейки. У каждого игрока
не более одной змейки; её player_id ссылается на PLAYING в players.

### Транспорт и область применения

Каждое сообщение содержит `protocol_version = 2`.
Клиент автоматически показывает игры из двух источников: локальное обнаружение
через IPv4 multicast **239.192.0.4:9193** и unicast-каталог фиксированного сервера
курса, доступного через Интернет. Адрес и UDP-порт сервера предоставляет курс;
они заранее заданы в конфигурации клиента, пользователь их не вводит для просмотра списка.
Другие версии игнорируются без ACK. Multicast-обнаружение рассчитано только
на локальную сеть: его работа через NAT и Интернет не требуется. Unicast-обмен
должен работать и через Интернет, в том числе с сервером по публичному IPv4-адресу
и UDP-порту. Клиент за NAT инициирует обмен с сервером из своего игрового UDP-сокета
и принимает ответы на наблюдаемый сервером endpoint. Используется только IPv4
для multicast и unicast.

Достижимость сервера через NAT не гарантирует прямой связи между клиентами.
Failover и приглашение сервера в клиентскую игру требуют достижимости нового
MASTER и остальных нужных endpoints; эти сценарии проверяются в сети с прямой
UDP-связностью (например, LAN, VPN или публичные endpoints). Реализовывать
STUN/TURN, hole punching или relay для произвольных пар клиентов не требуется.
Адреса участников — четыре десятичных октета 0..255 через точку, без ведущих
нулей (кроме самого 0), не более 15 ASCII-байт. IPv6, IPv4-mapped IPv6, имена
хостов и нестандартные сокращённые записи в GamePlayer.ip_address не допускаются.

### Идентификация игры и размер сообщений

Игра определяется именем `game_name` и endpoint обслуживающего её MASTER.
На одном сервере имена активных игр уникальны; имя не меняется при смене MASTER.
Все игровые сообщения содержат game_name в оболочке; в Join оно совпадает с
JoinMsg.game_name. DiscoverMsg не требует имени, а AnnouncementMsg содержит имена
в каждой записи GameAnnouncement и не требует имени в оболочке. Одинаковые имена
на разных серверах не означают одну игру. Повторное использование имени после
завершения игры не позволяет надёжно отличить все старые пакеты от новой сессии;
это документированное ограничение протокола без отдельного идентификатора сессии.

Одна UDP-датаграмма содержит ровно один сериализованный GameMessage без обрамления,
не более **1200 байт** с оболочкой. Ограничения поля, имён и числа участников
ограничивают размер состояния; перед отправкой проверяется фактический размер.
Молча обрезать сообщения нельзя. Некорректные или превышающие лимит входящие
датаграммы игнорируются. Прикладное разбиение сообщений не предусмотрено.
Лимит 1200 байт уменьшает риск IP-фрагментации; тестовая сеть должна поддерживать
IPv4 MTU не менее 1228 байт без дополнительных IP options. Изменять еду или тело
змейки ради размера пакета нельзя: фиксированные лимиты обеспечивают вместимость.
Превышение исходящего лимита — ошибка реализации: пакет не отправляется, игра
завершается с понятной ошибкой. Верхняя оценка State при этих ограничениях — **1145 байт**, включая оболочку,
максимальные положительные счётчики и ID, имена, IPv4-адреса, четыре змейки
по 32 клетки с поворотом на каждом шаге и 14 еды; это проверяется тестом.
Неизвестные поля protobuf не копируются в исходящие
снимки; необязательные поля оболочки без назначения не добавляются.

### Обнаружение игр

Два UDP-сокета: один только принимает multicast на 239.192.0.4:9193, второй
делает всё остальное, включая отправку multicast, и bind-ится на порт ОС.
Multicast-группа принимается на **всех доступных IPv4-интерфейсах с поддержкой
multicast**, а не только на интерфейсе маршрута по умолчанию. MASTER отправляет
свои multicast-анонсы через каждый такой интерфейс. Для нескольких экземпляров
на одной машине multicast-сокет настраивается на совместное использование порта
согласно ОС.

MASTER каждую секунду отправляет AnnouncementMsg с ровно одной игрой и отвечает
на DiscoverMsg unicast-анонсом. Пока показан список игр, клиент параллельно
принимает локальные multicast-анонсы и раз в **1000 мс** отправляет DiscoverMsg
на фиксированный сервер курса из игрового UDP-сокета. Сервер отвечает
unicast-анонсами своих игр; каталог может приходить несколькими AnnouncementMsg.
Если курс задаёт DNS-имя сервера, клиент разрешает его в IPv4-адрес;
GamePlayer.ip_address по-прежнему содержит только числовой IPv4-адрес.

Игры из обоих источников показываются в **одном списке**, записи объединяются
по (game_name, endpoint MASTER). Одинаковые записи с разных интерфейсов
или источников не дублируются; одноимённые игры разных MASTER остаются отдельными.
Каждая запись обновляется независимо, отсутствие обновлений в течение **3000 мс**
удаляет только эту запись. Ответ с частью каталога не заменяет список целиком.
Недоступность сервера, отсутствие multicast или ошибка одного интерфейса
не блокируют интерфейс и получение игр из остальных источников.
При подтверждённом failover обновляется адрес выбранной игры.
Discover и Announcement не подтверждаются. Все остальные сообщения — unicast.

В GamePlayer адрес и порт отправителя State/Announcement опускаются и берутся
из UDP-пакета. Endpoint остальных участников передаётся явно. При failover новый
отправитель опускает собственный endpoint, а старый MASTER передаётся явно,
если остаётся подключённым.

### Присоединение к игре

Создатель получает ID, MASTER и PLAYING; змейка размещается по правилам ниже.
Другой участник выбирает имя и endpoint игры и посылает JoinMsg с именем, типом и requested_status.

- VIEWING не требует свободного места и не создаёт змейку. При полном поле
  смотреть можно, если не исчерпан лимит участников.
- Для PLAYING применяются правила появления змейки из раздела «Правила игры».
  Нет места или уже четыре змейки — ErrorMsg; участник не добавляется.
- При успехе выдаётся новый ID, NORMAL, запрошенный статус и 0 очков.
  ACK на Join содержит receiver_id с выданным ID, затем приходит состояние.
  При необходимости назначается DEPUTY. can_join в анонсе относится к PLAYING;
  возможность просмотра ограничена только числом участников.
- При отказе посылается ErrorMsg с request_seq исходного Join, вместо ACK
  на Join. ErrorMsg имеет собственный новый msg_seq и подтверждается ACK.

### Подключение до получения конфигурации

Если конфиг ещё неизвестен (например, сервер создаёт игру по Join), клиент
повторяет Join с прежним msg_seq каждые **100 мс**, как и остальные запросы. После ACK на Join повторы Join
прекращаются; до получения конфига клиент отправляет Discover каждые **500 мс**.
Конфиг принимается из Announcement выбранного endpoint с выбранным game_name.
Общий срок получения ACK и конфига — **5 секунд** с первого Join; повторы и ACK
не продлевают его. Error завершает попытку раньше. Интервалы повторов и Ping
не зависят от наличия конфига; таймер связи запускается при успешном Join
(на клиенте — после ACK, на MASTER — после допуска участника).

Корректные State/Ping подтверждаются даже до получения конфига. State пока
не применяется: сохраняется только снимок с наибольшим state_order. Если State
пришёл раньше ACK на Join, его receiver_id должен совпадать с ID собственного
endpoint в players; последующий ACK на Join должен подтвердить тот же ID.
После получения ACK и конфига снимок проходит полную проверку и применяется,
таймеры связи продолжают работать без изменения интервалов. При истечении срока буфер освобождается,
пользователь получает ошибку; если ID известен, клиент может отправить Leave,
иначе MASTER удалит недоступного участника по тайм-ауту.
При восстановлении Join поиск нового анонса ограничен отдельными 3 секундами
из раздела «Смена MASTER»; смена endpoint начинает новую попытку подключения.

### Команды управления

Состояния сменяются раз в state_delay_ms. Между ходами PLAYING отправляет SteerMsg
MASTER. Используется последняя допустимая команда по msg_seq до начала расчёта хода.
Разворот в клетку шеи запрещён и проверяется по текущему телу, а не промежуточной
команде. Недопустимая команда не отменяет предыдущую допустимую. Опоздавшая команда
рассматривается для следующего хода. VIEWING не отправляет команды управления.

### Подтверждения, повторы и таймеры

Новые сообщения получают возрастающий неотрицательный msg_seq. Повтор сохраняет
номер и содержимое. **ACK — исключение**: копирует номер исходного сообщения,
не расходует счётчик отправителя и не участвует в сравнении новизны команд.
При исчерпании счётчика участник выходит, а не обнуляет его.
Счётчик ведётся на протяжении всей сессии участника, включая повторное вступление
в игру с того же сокета. Для новой сессии используется новый UDP endpoint,
чтобы старые запросы не совпали с новыми.

Все сообщения, кроме Announcement, Discover и ACK, требуют ACK. Для отклонённых
Join/PlayerStatusChange вместо ACK приходит Error с request_seq запроса;
сама Error требует ACK по собственному msg_seq. Ошибка завершает только тот запрос,
на который ссылается request_seq.

После проверки версии, game_name, endpoint и ID ACK обрабатывается отдельно:
его msg_seq сопоставляется с неподтверждённым исходящим сообщением к этому endpoint.
ACK не помещается в кеш входящих запросов, не продвигает окно дедупликации
и никогда не подтверждается. Несопоставленный ACK игнорируется. ACK и обычное
сообщение одного отправителя с одинаковым msg_seq не мешают друг другу.

Без ответа сообщение повторяется каждые **100 мс**, независимо от state_delay_ms
и наличия конфига. Только сообщения, требующие ответа,
дедуплицируются по (game_name, адрес, порт, msg_seq): повтор получает прежний ответ,
но операция не выполняется снова. Повтор Join возвращает тот же ID, а не новую змейку.
Один endpoint может представлять не более одного подключённого участника игры.
Новый Join уже подключённого endpoint возвращает имеющийся ID без новой змейки;
для изменения статуса используется PlayerStatusChange. Проверка сохранённого
ответа на повтор выполняется до проверки текущего участия: это позволяет
подтвердить повтор Leave после удаления участника.
Ответы хранятся в окне **1024 номеров** для каждой пары (game_name, endpoint).
Если H — наибольший принятый номер сообщения, требующего ответа, окно содержит
номера max(0, H - 1023)..H. Пропуски допустимы: счётчик общий для адресатов и типов.
Только корректное сообщение с допустимыми полномочиями может продвинуть H;
сохранённый ответ на повтор проверяется до проверки текущего членства.
Номер ниже окна игнорируется без ответа и никогда не исполняется заново.
Это исключение имеет приоритет над подтверждением устаревших команд и State.
Повтор Leave после удаления участника получает прежний ACK, пока номер в окне.

Окно и watermark H вышедшего endpoint сохраняются до конца игры; повторное
вступление с него продолжает тот же счётчик. Число записей endpoint и общий объём
кеша ограничиваются заранее заданным бюджетом. При его исчерпании прекращается
допуск новых endpoint; записи защиты не удаляются ради нового Join. Для Join,
ответ на который нельзя сохранить, допускается только отказ без изменения игры:
Error с новым msg_seq при каждом повторе либо игнорирование при перегрузке.
Память окон уже допущенных участников резервируется, чтобы бюджет не препятствовал
их обслуживанию.

Отправитель прекращает повтор запроса, если уже отправил этому endpoint сообщение,
требующее ответа, с номером на 1024 или более выше: запрос мог выйти из окна.
Результат Join выясняется новым Join с новым номером с того же endpoint
(возвращается существующий ID), результат смены статуса — по текущему State;
при необходимости посылается новый запрос с новым номером. При неопределённом
результате Leave клиент закрывает сессию, далее действует тайм-аут.
Уведомления восстанавливаются из актуального State; новые State/Ping продолжают связь.
Подтверждение старой операции после выхода из окна не гарантируется.

Одновременно неподтверждённых исходящих
сообщений к одному соседу — не более 64; новые Steer и State могут заменять
устаревшие того же типа, но управляющие операции не теряются из-за лимита очереди.

Steer и PlayerStatusChange имеют отдельные проверки порядка по msg_seq.
Запоздавшая команда не отменяет более новую, но подтверждается. State с
state_order не больше последнего известного подтверждается, но не применяется.
Неверные версия, game_name, endpoint или полномочия не меняют состояние.

sender_id/receiver_id обязательны в unicast зарегистрированных участников.
Join до регистрации не имеет sender_id; отказ на Join может не иметь receiver_id,
а ACK такого отказа — sender_id. Их сопоставляют по game_name, endpoint и номерам.
Discover и Announcement не требуют receiver_id, в том числе при unicast-ответе
на Discover от ещё не зарегистрированного клиента. ID проверяется вместе с endpoint.

Если соседу не отправляли unicast за **100 мс**, отправляют Ping.
Любое корректное unicast, включая ACK, обновляет таймер связи. Отсутствие сообщений
в течение **1000 мс** означает предполагаемый отказ. После удаления соседа
его повторы прекращаются; исключение — перенос запросов при failover.
Эти фиксированные интервалы действуют при любой скорости игры, включая
state_delay_ms=3000: связь поддерживается Ping между ходами. Анонсы отправляются
раз в 1000 мс, устаревают через 3000 мс; Discover при получении конфига — раз
в 500 мс; обычный опрос каталога сервера при просмотре списка — раз в 1000 мс.
Срок начального подключения — 5000 мс. Все интервалы измеряются
монотонными часами.

### Смена MASTER

Топология — звезда; только MASTER меняет состояние и рассылает его всем,
включая VIEWING. DEPUTY хранит последнюю применённую копию, конфиг и счётчик ID.

- MASTER при потере NORMAL/DEPUTY удаляет участника и его змейку
  и при необходимости выбирает нового DEPUTY.
- NORMAL любого статуса при потере MASTER переключается на последнего известного
  DEPUTY. Если его нет или он также недоступен, сессия заканчивается с ошибкой;
  самостоятельно NORMAL не становится MASTER.
- DEPUTY при потере MASTER становится MASTER, продолжает последнюю принятую
  копию, удаляет прежнего MASTER и его змейку. Назначает
  нового DEPUTY и уведомляет всех NodeRoleChangeMsg и StateMsg. Первый новый
  state_order больше последнего принятого; game_name, конфиг, очки и статусы сохраняются.

Неподтверждённые запросы к старому MASTER продолжают повторяться новому:
номер и содержимое сохраняются, меняются только адрес и receiver_id.
Если endpoint повторного Join уже есть в унаследованном состоянии, возвращается
его существующий ID. Незарегистрированный клиент после тайм-аута выбирает новый
анонс с тем же game_name и повторяет Join; отсутствие нового анонса в течение
3 секунд завершает присоединение с ошибкой.

Примечание: для такого восстановления Join совпадения game_name достаточно;
проверять преемственность через прежнего DEPUTY не требуется. Если разные серверы
объявляют одно имя, клиент может присоединиться к другой одноимённой игре.
Это осознанное ограничение восстановления по имени; используйте различимые имена,
если такая неоднозначность нежелательна.

Изменения, не успевшие дойти до DEPUTY, могут потеряться. Ровно однократное
исполнение через отказ MASTER не гарантируется; источник истины — новый MASTER.
Пакеты прежнего MASTER после переключения игнорируются.

Предусмотрен failover при отказе одного узла. Сетевая изоляция части участников
(partition) и согласование двух MASTER не входят в задание. Тайм-аут означает
подозрение на отказ, а не доказательство; при partition возможны две версии игры.
Объединять их не требуется: после восстановления сети пользователь выходит
и присоединяется заново.

### Запрос статуса и выход

Интерфейс разделяет **«Смотреть / прекратить играть»** и **«Выйти из игры»**.
PlayerStatusChange от участника к MASTER — запрос собственного статуса:

- PLAYING -> VIEWING удаляет змейку;
  ID, очки и сетевая роль сохраняются.
- VIEWING -> PLAYING размещает новую змейку по правилам Join. ID и очки
  сохраняются. Нет места или уже четыре змейки — Error, статус остаётся VIEWING.
- Запрос текущего статуса успешно подтверждается без изменений.

Успех подтверждается ACK. PlayerStatusChangeMsg передаётся только от участника
к MASTER; сообщение в обратном направлении игнорируется. MASTER публикует
новый StateMsg сразу после изменения. При запросе текущего статуса отправляется
актуальный StateMsg без увеличения state_order. Только принятый StateMsg задаёт
фактический статус и наличие змейки: ACK завершает запрос, но сам статус не меняет.
До снимка интерфейс может показывать ожидание; устаревшие снимки отбрасываются
по state_order. Смерть отражается в StateMsg того же хода.

Смерть меняет статус на VIEWING, **но MASTER остаётся MASTER, DEPUTY — DEPUTY**.
При полном выходе посылается LeaveMsg. MASTER подтверждает, удаляет участника
и его змейку. На повторный Leave в пределах окна дедупликации
возвращается прежний ACK, даже после удаления участника; ниже окна запрос игнорируется.
Не получив ACK, можно всё равно закрыть программу:
остальные обработают выход по тайм-ауту.

Выходящий MASTER сначала передаёт актуальный State DEPUTY и ждёт ACK, затем
посылает NodeRoleChange с sender_role=NORMAL, receiver_role=MASTER и ждёт ACK.
Его state_order — номер следующего состояния, которое опубликует новый MASTER.
DEPUTY принимает управление, удаляет вышедшего MASTER и уведомляет остальных.
Ожидание ограничено тайм-аутом связи: при неудаче MASTER всё равно выходит,
далее работает обычный failover. NodeRoleChange принимается только от текущего
MASTER (назначение/передача управления) или известного DEPUTY при failover.
Участник не может сам назначить себе сетевую роль произвольной командой.

## Требования к ресурсам

Число тредов ограничено заранее известной константой и не зависит от числа
игроков, змеек, еды, перезапусков или смен MASTER. Потери, дублирование
и перестановки UDP-пакетов обрабатываются без блокировки интерфейса
и утечки ресурсов.
